OpenCode v2 loads the skills natively from `~/.agents/skills`. No extra skills install step is needed. The installer also writes a plugin when the OpenCode config directory already exists. It never creates that directory for you.

## What the installer writes

The installer picks one config directory, using the first nonempty value:

1. `OPENCODE_CONFIG_DIR`.
2. `XDG_CONFIG_HOME` with `/opencode` appended.
3. `~/.config/opencode`.

It writes `plugins/skills.ts` there and records the file's SHA256 hash in `.skills-install.json`. It never uses `~/.opencode`, which OpenCode treats as a project directory. A session started with a different `OPENCODE_CONFIG_DIR` does not get this plugin.

The plugin entry is a small written stub. It imports `playbook/opencode/plugin.ts` through the absolute `AGENTS_DIR` path, so changes in the linked checkout take effect without copying the plugin again. If that import fails or does not yield a plugin, the stub refuses every shell call with a message naming the path and the cause. The plugin's id is `skills-guard`; a config that disables that id turns the guards off.

The manifest records the bytes this installer wrote. An existing file is owned only if its hash still matches that record. An edited or unrecorded file, a symlink or a directory is personal and stays untouched, with a skip line in the install output. Missing files are created and recorded. An unchanged install leaves the plugin and manifest byte identical and prints nothing for them. An invalid or unreadable manifest is left alone, and writes that need it are skipped.

## What the plugin guards

The plugin maps OpenCode tool inputs to the existing CLI payloads and forwards their verdicts. It decides no policy itself.

- Before `shell`, it runs `skills hook pre-tool-use`. A refusal throws the [commit guard](/hooks/commit-guard)'s exact reason into the tool result. A renamed tool with a string `command` input gets the same check.
- After a completed `edit`, `write` or `patch`, it runs `skills hook post-tool-use`. A [comment](/hooks/no-comments) or [dash](/hooks/no-em-dash) finding goes first in the tool's content, before the original output.
- Other tools, including `read`, run no hook. Failed edits run no post hook.

The CLI needs Bun. Without it, every shell call is refused, and the installer prints a note saying so. An unreadable pre-hook result, a failed launch or a timeout also blocks the shell call. Each CLI invocation has a 30 second timeout. A post-hook failure leaves the original result untouched and never fails the tool call.

This plugin does not wire the session brief or reply guard. The installer adds no OpenCode agents or permission rules.

## Instructions and service environment

OpenCode reads global instructions only from `<config dir>/AGENTS.md`, with no `CLAUDE.md` fallback. The installer manages no `AGENTS.md` for any host. Put your own instructions there.

Plugins run in the server process. The background service keeps the environment of the client that started it. Setting `AGENT_HOOKS=0` on a later client does not reach the running plugin. Use a standalone run when changing that environment:

```sh
AGENT_HOOKS=0 opencode run --standalone "Your request"
```

As on the other hosts, `AGENT_HOOKS=0` turns off the comment and dash guards, not the commit guard. See [Configuration](/reference/configuration#hooks-and-skills) for hook settings.

## Verify an install

The repository's `scripts/verify-opencode.ts` installs into a temporary home and config directory, then asks a real OpenCode v2 model to attempt a guarded shell call against a local bare remote. It prints whether the plugin loaded, whether the shell call returned the commit guard's reason, and whether the remote stayed unchanged. It runs by hand, never in CI, and calls a paid model. It retains your real `HOME` so OpenCode can use its saved authentication.

```sh
bun scripts/verify-opencode.ts opencode-go/glm-5.3-flash
```

The model may also be set with `OPENCODE_MODEL`; the command line argument wins.
