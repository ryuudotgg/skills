## /plans do `[id]`

With no id, run `<playbook>/bin/skills plans frontier --next <Project>` and use the id it prints. Empty output means nothing is ready, so say so and stop.

One thread works one plan in one checkout. Threads in separate worktrees never touch each other, so any number of plans can be DOING at once. A row is a live thread while it is DOING, and it holds the checkout its branch is in. The live thread rule: `/plans do` refuses when the current branch belongs to another DOING row, since cutting a branch would take that thread's checkout, and when a blocker is DOING, since a fix round may rewrite it under the new layer. In hands-off mode a handed back row stays DOING until `/plans close`, so there both cases only warn. A dirty tree refuses in both modes, which also covers a blocker holding uncommitted work.

a. Read the plan and its ctx file. Nothing else from `<plans>`, no sibling plans, no `done/`, except the resume note of an adopted plan, per step b. The playbook skill's Backlog item playbook owns the destination gate, the probe and the route. That skill is user-invoked, so no tool call reaches it and no skill can fire it: open it from disk instead. Read `<playbook>/SKILL.md` in full, then `<playbook>/playbooks/backlog-item.md`, and follow them exactly as if the operator had typed `/playbook`, pausing after its step 0 gate for step b below. Do not run the probe before the branch exists; it runs once, on the new branch, so it sees the base's code.

b. Start the plan with `<playbook>/bin/skills plans start <Project> <id>`. It picks the base, clears the layers below it, cuts the branch, sets the row DOING with that branch and logs `start`, then prints the base and the updated row. Rerun on that branch after a failed row or log write, it finishes both without cutting again. It asks `gh` for each open blocker's PR. A PR merged into the default branch releases its blocker even when the row still reads REVIEW. With nothing unmerged the base is the remote default branch after a fetch of that branch alone. Otherwise the base is the unmerged blocker branch that contains all the others, and it must also contain every merged blocker's merge commit. It cuts `feat/<slug>` from the base with no upstream and records the base as `git config branch.feat/<slug>.skills-base`. Whenever it cannot pick a base holding every blocker's work it refuses, naming the reason, before any branch exists: a dirty tree, the live thread rule above, blockers on two chains, a blocker with no PR or a closed unmerged one, and a missing `gh` among them. A TODO plan whose `needs:` this machine does not meet refuses first, with `<id> needs <cap>, this machine lacks it;` and `run on <labels>` naming every other machine whose facts meet it, or `no known machine has it`: paste `/plans do <id>` into a thread on one of those machines. The branch carries the descriptor only, no plan id; the index row's branch column is how "which plan was this" gets answered later. Once it succeeds, in T3 Code, bind this thread to the row with `<playbook>/bin/skills plans log <Project> <id> thread <threadId>`, the `currentThreadId` that `t3_thread_list` returns, so `/plans resume` can find it. Once per thread in T3 Code, also run `<playbook>/bin/skills machine refresh --environment <environmentId>` with the `environmentId` that `t3_environment_read` returns, so this machine's facts name the T3 environment it runs in.

   **An adopted plan.** `plans adopt` leaves the row DOING on its branch, checked out in the checkout it adopted into, with its resume note at `<plans>/<Project>/.resume-<id>.md` and an `adopted` event as the row's newest move. When the frontier lists the row DOING on the branch checked out here, with no mark after the branch, the row's newest `start` or `handback` line in `<plans>/log.tsv` is a `start`, since a handback releases the lease adopt took, and that note exists, the plan was adopted here and this is a pickup, the one exception to running `plans start` on an existing branch. A stale mark counts as no mark only when `<playbook>/bin/skills machine show` prints `device -`, since a store with no hub holds this machine's events alone; with a hub a label proves no ownership, as two machines can share one. Any other mark, `(moving to ...)`, `on <label>`, `conflict with <label>` or a stale mark under a hub, means the plan may have left this machine or another machine may hold it, so that row goes through `plans start` and its refusal. Run neither `plans start` nor `plans stack-base`: the branch, its recorded base and the lease are already in place. Read the note before opening any source file, as the Session pickup playbook reads its trail, and treat the adopted commits and the uncommitted diff as work already done. Leave that diff in place, with no reset, stash or checkout, until the delivery mode's handback takes it, and leave the note where adopt wrote it. Bind the thread and refresh the machine facts as above, then go to step c, where the probe runs on the adopted tree and the route resumes at the note's next step. Probe outcome (a) does not close an adopted plan when the adopted commits or diff are what make its criteria hold: that is this plan's own unpublished work, so verify it and hand it back as step d says. A row that misses any of these facts, and any other existing branch, goes through `plans start` and its refusal as usual.

   **The preflight, prs mode only.** When the base is a branch, not the remote default branch, `plans start` runs the `plans below` check on it before cutting. It reads every open PR in the base's recorded chain and refuses when any of them still has an unresolved thread an installed reviewer started (`<playbook>/references/reviewers.md`), whoever has joined it since, printing one `open` line per thread with its row id, branch, PR number and comment URL. Resolution is read from GitHub's own thread state, so a thread resolved on the PR never counts, whatever the inline comments still show. It also refuses on a layer that is not owned, or whose PR is missing or closed unmerged. Clearing those threads is the operator's step, normally already done by the babysit that ran before this plan was named. Hands-off mode skips the preflight.

   On any refusal, quote it and stop: nothing is cut, the row stays TODO, and nothing below is checked out, fixed or pushed. The standalone `plans set-row` and `plans log` stay for `/plans review` and handoff, and `plans stack-base` and `plans below` stay as operator tools.

c. Resume the Backlog item playbook at its probe. If the probe stops at outcome (c), set the row back to TODO with `plans set-row` so it holds no live thread, and leave the branch for the operator.

   **Work another project must do.** When the plan cannot land without a change in another project's code, file that change into the other project's inbox instead of making it: `<playbook>/bin/skills issues file <Target> "<title>" --from <Project>/<id> --blocks <Project>/<id>`, which prints the issue ref and adds it to this row's `blocked_by`. Never file one for work this plan's own Outcome covers. Then discard this plan's uncommitted paths, so the rerun starts on a clean tree, run `<playbook>/bin/skills plans set-row <Project> <id> BLOCKED - "waits on <Target>#<n>"` and `<playbook>/bin/skills plans log <Project> <id> handback feat/<slug>`, publish nothing, and hand back BLOCKED with the ref in the reply so the operator can watch it. When the issue closes and the row waits on nothing else, it goes back to TODO on its branch and `/plans do <id>` picks it up there.

d. The playbook's handback decides the end. Run `<playbook>/bin/skills delivery` by its absolute path, never through `sh`, and quote its output.

- **hands-off.** The work lands unstaged on that branch. Do not commit it, do not stage it, do not push it, do not open a PR. End by reporting what changed and suggesting one conventional commit message: single line, 50 chars maximum, no body, no trailers, describing the actual change. Write the landed draft, per The landed draft above. Then `<playbook>/bin/skills plans log <Project> <id> handback feat/<slug>`.
- **prs.** The handback publishes through `<playbook>/bin/skills publish` and prints the PR URL. A refusal or a failure there ends the thread with the row still DOING; a rerun after the fix reuses the pushed branch and the open PR. Once the PR is open, write the landed draft, per The landed draft above, and keep it current through the babysit's fix rounds. Then run `<playbook>/bin/skills plans handoff <Project> <id>`. It names the ready plans that would stack on this layer, every DOING row on the branch counted as the layer, and leaves the rows DOING. Quote its output.
  - **`babysit`.** The first line lists the branches of this layer's stack, bottom first; each `next` line after it is a ready plan that stacks on this layer. In this thread, run the Babysit playbook in `drive` mode on the PRs of those branches, bottom first, with the reviewer round `<playbook>/bin/skills round` drives when the mode lists a reviewer. Its prs delivery section sets every owned row to REVIEW when it stops, which `plans set-row` allows only for a green PR; then `<playbook>/bin/skills plans log <Project> <id> handback <branch>`. The reply is the babysit's. Name each `next` id as the plan to start with `/plans do <id>` in a fresh thread only when the babysit stopped at the handoff state, a combined `done` from `skills round` included, which every reviewer being `absent` meets. On any other stop, say the `next` ids wait on this layer and name what stands in the way. This thread starts none of them.
  - **A refusal.** Report it verbatim and stop.

## /plans do `<ctx-slug>`

One thread works every ready XS and S plan of one ctx on one branch and publishes them as one PR, one commit per plan. It runs only when the operator names a ctx, and only in prs mode: a hands-off batch could not keep one commit per plan. `/plans do` with no argument and `/plans wave` never start one.

a. Read the ctx file, then the playbook files as `/plans do` step a says. Each member's plan is read when its turn comes, never before.

b. Run `<playbook>/bin/skills plans start <Project> <ctx-slug>`. It takes every TODO row of that ctx sized XS or S whose blockers are DONE, DROPPED or themselves members, so a member waiting on a row outside the batch stays out, and so does every member waiting on it. It cuts `feat/batch-<ctx without ctx->` from the remote default branch after a fetch, taking `-2`, `-3` and so on while a local branch, a branch on origin or any index row's branch already holds the name, records the base, sets every member DOING on that branch in one index write, and logs `start` for each. It prints the base, the member rows in commit order (blockers first, then priority, then id), and one `left <id> <reason>` line per ctx row it leaves TODO, a member this machine does not meet among them. Rerun on that branch after a failed write, it finishes the claim without cutting again and prints the rows it holds. It refuses on a dirty tree, the live thread rule, a checkout of another project, hands-off mode, or no member. Bind this thread to each member with `plans log`, as `/plans do` step b says.

c. Work the members in printed order, each on a clean tree. For each one, run the Backlog item playbook from its step 0 gate on that member's plan, through its probe, route, implementation and its own `## Acceptance` evidence, then the standing checks. A member is committed only once its own evidence exists, so a failing plan never rides in on a sibling's green: `git add <its files>`, then `git commit -m "<its own Conventional line>"` in a separate call. Probe outcome (a) closes the row DROPPED with its landed draft. Probe outcome (c), or a member whose checks cannot pass, leaves the batch: discard its uncommitted paths, set it back with `plans set-row <Project> <id> TODO - "<why>"`, do the same for every later member it blocks, and go on to the next member. Its branch column keeps the batch branch as a trace, and `plans start` refuses a plan that waits on it until it starts again.

d. The last committed member's files go through `<playbook>/bin/skills publish -m "<its line>" -t "<one Conventional line naming the batch>" <its files>`, which opens the one PR for every commit. No commit at all means nothing to publish: report each member's outcome and stop. Then write each committed member's landed draft, per The landed draft above, each with `Branch feat/batch-<...>, not merged yet.` and only what that plan shipped. Then `/plans do` step d runs as written with any member's id: `plans handoff` treats every DOING row on the branch as the layer and names the plans that stack on any of them, the babysit runs on that one branch, and when it stops every member still DOING goes to REVIEW with `plans set-row` and gets its own `handback` log line. A member that left the batch keeps its TODO or DROPPED row through all of it. A later `/plans review <id>` on any member is the round for the whole PR: it sets every member DOING, REVIEW or BLOCKED on the branch DOING and logs `review` for each, and at its end sets each of them REVIEW, or BLOCKED, and logs each `handback`. The sweep closes every member once the PR merges, each landed draft stamped with the same merge.
