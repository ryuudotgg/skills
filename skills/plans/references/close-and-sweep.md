## /plans close `[id]`

With an id, steps 1 to 3 close that one plan. With no id, the sweep below closes each merged plan whose thread has finished and reports the rest. `/plans wave` runs the same sweep before it launches.

1. The plan file already carries its landed draft, per The landed draft above. A plan handed back before that rule has none: write it now, in the same shape.

2. `<playbook>/bin/skills plans close <Project> <id> DONE "<note>"` (or `DROPPED`). It sets the row, moves `<id>-<slug>.md` into `done/` and appends one `done` log line carrying the note, then prints the row. On DONE it also rewrites the draft's first line to the merged line, reading the row's PR with `gh`; it refuses while that PR is unmerged, and `--sha <sha>` names the merge commit when `gh` cannot. DROPPED leaves the draft as written. `--dry-run` prints the row and the rewritten line and writes nothing. It refuses a plan file with no `## Landed` section, so step 1 comes first. Rerun on a closed plan, it changes nothing and prints `<id> is already closed`; after a partial run it does only the steps still missing. The note is capped at 100 chars and the verb enforces it. If the reason needs more room, that is the signal it belongs in `## Landed`.

3. When the harness lets an agent settle its own thread, settle this one as the turn's last call, after the last close. Settling marks the thread's work done. The thread leaves the operator's active list and stays in their history. Archiving or deleting is not settling, so a harness that offers only those has no settle. Skip the settle when any close refused. Skip it too when the current branch belongs to a DOING row, since this thread still works that plan.

### The sweep

`/plans close` with no id, run from the project's checkout. `/plans wave` runs it as its first step, and `/plans schedule` registers it as a recurring task when `PLANS_SWEEP_EVERY` is set. It never settles the thread it runs in; the scheduled task's prompt asks for that settle itself.

1. Run `<playbook>/bin/skills plans sweep <Project> --json`. It prints one JSON object: `lines`, the sweep's lines, which you quote verbatim, then `conflicts` and `busy` for step 4. It reads each DOING and REVIEW row's PRs by the row's branch with `gh`, counting only a PR that is open or that closed after the row's last `start` in `log.tsv`, so an older PR on a reused branch never closes a newer row. A row's thread counts as live while its last `start` or `review` in `log.tsv` has no `handback` or `done` after it. Each REVIEW row whose PR merged into the default branch, and each such DOING row whose thread is not live, gets the same close as `plans close <id> DONE`, with the PR title as the note and the merge stamped into the landed draft: `closed <id> #<pr> <slug>`. A merged DOING row whose thread is live prints `live` and closes on a later sweep. A REVIEW row whose open PR GitHub reports as conflicting prints `conflict <id> #<pr> <sha>` with the PR's head, or `sent <id> #<pr> <sha>` once `log.tsv` holds a `conflict-sent` event for that head. Every other row gets one line: `open`, `unmerged` (closed without merging, the operator's call, never DROPPED), `elsewhere` (merged into a branch other than the default), `nopr`, `skipped` (the row's branch is the default branch), `unstarted` (merged, but no `start` dates the row, so close it by id), `unreadable`, `already`, `refused`, or `draft` (merged, with no `## Landed` section). Then one `checkout <id> <path> <state>` line per checkout of a closed row's branch that no open row shares, this run's closes and earlier ones alike. Then it removes `/tmp/plans-<id>/` for each of the project's closed rows, `removed <path>`, unless a row with that id in any project holds it: one still open, one back in TODO after a start, or one closed while its thread is live. An unreadable index or trail holds every one. Each removal claims its directory under a lock `plans start` also takes, so no row starts between the check and the removal. A held directory prints `kept <path>: <reason>` for a row closed in this run or an unreadable file. It ends with `closed <n> of <m>`, or `nothing left to close` when no merged row stayed open, and exits 1 when a row merged into the default branch stayed open for any reason but a live thread, or a read or a removal failed. `--dry-run` prints `would close` and `would remove` instead and writes nothing.
2. For each `draft <id> #<pr> <plan file>` line, write the landed draft into that file, per The landed draft above, from `gh pr view <pr> --json title,body,headRefName,mergeCommit` and the last reply in the row's thread, then run the sweep once more. In T3 Code the row's thread is the one its last `thread` event in `log.tsv` names, else the one `t3_thread_list` lists in this project with that PR in its `pullRequests`, else the one titled `plans <id> <slug>`. With no thread, write it from the PR alone.
3. When the harness can settle another thread (in T3 Code, `t3_thread_organize` with `settle` and that thread's id), settle the thread of each `closed` row, found as in step 2, and every other unsettled thread `t3_thread_list` shows in this project whose row the index now holds as DONE or DROPPED, never this thread. Leave a thread that is preparing, queued, starting, running or waiting, and name it.
4. Each `conflicts` entry is one `conflict` or `sent` line: `id`, `slug`, `pr`, `sha`, the `thread` its last `thread` event names or null, and `sent`. An entry with `sent` true already has `/plans review <id>` waiting for that head, so leave it. When `busy` is null the checkouts could not be read, so send nothing this sweep. For each other entry, in T3 Code, find the row's thread as in step 2, and read it with `t3_thread_read` and `runLimit` 1. Send nothing when it is preparing, queued, starting, running or waiting, when its `worktreePath` is a key of `busy` naming another id, since that checkout holds a DOING row's branch, or when this sweep already sent into that checkout; name it in the reply and let the next sweep try again. Otherwise send `/plans review <id>` with `t3_thread_send`, `mode` `queue` and `clientRequestId` `conflict <id> <sha>`, retrying a send that errors or loses its response with the same id. Once T3 accepts it, run `<playbook>/bin/skills plans log <Project> <id> conflict-sent <sha>`. A send that failed logs nothing, so the next sweep sends again. With no thread, or on a harness that cannot message threads, print `/plans review <id>` per entry for the operator to paste into the row's thread, and log nothing.
5. Reap, then release the candidates, after steps 2 to 4. It is the sweep's last act. Run `<playbook>/bin/skills reap <Project>` before anything else here and quote its lines, so no test artifact of a closed plan still works in a checkout the release would free. Its exit code changes nothing below: the release still runs, and holds any checkout a process the reap left still works in. In T3 Code, build the harness facts first, one entry per `checkout <id> <path> <state>` line, whatever its state. Find the row's thread as in step 2, read it with `t3_thread_read` and `runLimit` 1 and its queue with `t3_queue`, `action` `list` and that thread's id, and write `{"path": "<path>", "live": true}` when it is preparing, queued, starting, running or waiting, has a pending request, or holds a queued message, else `"live": false`. Settled has no part in it, since step 3 settles closed rows' threads. A row with no thread gets `"live": false`. A thread whose read or queue read fails gets no entry, so the verb holds its checkout. Pipe the array, `[]` when there is no `checkout` line, to `<playbook>/bin/skills plans release <Project> --facts`. On a harness with no threads, run it without `--facts`. Quote its output. The verb is the only thing that removes a checkout: run no `git worktree remove`, `git worktree prune` or `rm` on one yourself, whatever a `kept` line says.
6. Reply with the sweep's lines verbatim, a link to each thread settled, a link to each thread sent `/plans review` with its `conflict-sent` log line, each conflict held back and why, the reap lines verbatim, then the harness facts piped to `plans release` and its `released` and `kept` lines verbatim.

No plan file is deleted. A DROPPED plan keeps its `## Landed` section explaining what made it unnecessary, which is what stops it being re-proposed in six weeks.
