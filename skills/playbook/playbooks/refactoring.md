### Refactoring

**You own the contract. The structure changes; the behavior does not.** For "refactor", "rename", "extract", "inline", "dedupe", "restructure", "move this module", "tidy up this area". Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

A refactor that smuggles in a behavior change loses its safety net. The tell: a step that needs a test changed to stay green has changed behavior, unless that test pinned an implementation detail on purpose. If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. A redesign is allowed, but name it and route to Feature. Large or cross-cutting structural work (a migration across many call sites, a coordinated reshape of many subsystems) belongs to the **figure-it-out** skill; this playbook is the focused-to-medium change.

1. Pin the behavior contract first. Run the **how** skill over the affected subsystem to learn the contract, then write a characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves. The harness makes "refactor" a checkable claim (the **prove-it-works** principle skill). If the area has no coverage, write the pin before touching structure. Type check and lint are not a pin.
2. Name the structure the code is missing per the **model-the-domain** principle skill: a state machine over scattered booleans, a table or registry over spread-out branching, a typed model over repeated shape assumptions, a reducer over ad hoc mutations. Boring code stays when the shape is already clear and local; the reshape must delete branches or invalid states, not add indirection.
3. Name the target shape. State what the module layout, types, and call graph should be if built today (the **foundational-thinking** and **redesign-from-first-principles** principle skills). If the target crosses a function boundary, run the **architect** skill for parallel design exploration of the shape before the move.
4. Subtract before you add. Delete dead weight, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape (the **subtract-before-you-add** principle skill). The smallest change that reaches the target shape ships (the **laziness-protocol** principle skill). A speculative cleanup that "might help" gets reverted, not left to ride.
5. Move in small behavior-preserving steps, each keeping the pin green. For API reshapes, migrate every caller and delete the old API in the same wave (the **migrate-callers-then-delete-legacy-apis** principle skill). No compatibility shims, no parallel old-and-new paths. Spot-check every rename against the actual files; renames silently miss usages in strings, prose, and back-references. Delegate the mechanical edits to the `codex-terra` wrapper agent, which shells out to the Codex CLI (`codex exec --enable fast_mode -m gpt-5.6-terra -c model_reasoning_effort=medium -C <abs repo path> -o /tmp/codex/<slug>.md`), with a specific scope (file paths, the names being moved, the behavior to hold); review the diff yourself. A pure rename sweep can drop to `codex-luna`. Never pass an `isolation` parameter to a subagent; worktrees are banned.
6. Prove behavior is unchanged on the real artifact, not "it compiles" (the **prove-it-works** principle skill). For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface through a live browser MCP (Playwright or equivalent, tool names matching `mcp__*playwright*`) or whatever preview MCP the harness exposes. Own the verification yourself; do not trust a delegate's "looks good" summary.
7. Confirm the change earns its place. The success measure is reduced reader load (the **minimize-reader-load** principle skill): fewer layers between question and answer, less hidden state, fewer indirections without a second consumer. If the diff does not lower reader load somewhere, revert it.
8. Order the slices so they tell the story: the subtraction, then the reshape, then any follow-on cleanup, so one slice can be undone on its own. Shape them with the **sequence-verifiable-units** principle skill, so each behavior-preserving slice stays green before the next. The whole thing stays unstaged on one `feat/*` branch in the main tree; you never commit, never push, never rebase. Name the slice boundaries in the handback so the operator can split the commits. Run `handing-back.md`.

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped and what got reverted. No new behavior.
